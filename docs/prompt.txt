## PROC-0001 Documentation Review Campaign (status: active, v1.0.0, owner Rodolfo Garavito)
- Alcance: revisión humana de drafts de documentación de plataformas, en el repo
  Docusaurus de cada plataforma.
- Fuera de alcance: los artefactos del framework en andes-architecture, que se revisan
  por PR normal.
- El estado vive en Jira y en `docs-state.yml`:
  - un Epic por campaña,
  - una Story por área,
  - una Sub-task por archivo, con la ruta del archivo en la descripción.
- Fases:
  1. Backlog: el Orchestrator Agent crea el backlog.
  2. Assignment: el Tech Lead asigna.
  3. Concurrent Review: cada reviewer trabaja en su rama.
  4. PR Merge / Indexing: el Tech Lead mergea y el Orchestrator indexa en Context Forge por Story.
- Rama: `review/{reviewer}/{area}-{YYYY-MM-DD}`. Regla: un archivo = un reviewer = una rama.
- Al aprobar un documento:
  - `status: Published`
  - se actualiza `last_modified`
  - `source` pasa de AI_INFERENCE a BUSINESS_EXPERT (YYYY-MM-DD), según DM-0001
- Otros resultados posibles: pedir rework (el agente refina el documento) o "Needs Discussion".
- Gates:
  1. Backlog Complete
  2. Assignment Complete (owner: Tech Lead)
  3. Document Approved (owner: Reviewer)
  4. PR Approved (owner: Tech Lead)
  5. Story Complete → indexación incremental
  6. Epic Complete
- Métricas: tiempo a primera aprobación ≤ 5 días hábiles, tasa de rework ≤ 30%,
  cero conflictos de merge, balance de carga entre reviewers.
- La guía paso a paso vive en Confluence (Sección 3, "Manual Review Process") y en
  `diagrams/04-proceso-revision-manual-documentacion.mmd`.

# Hechos técnicos de Claude Code (docs oficiales, sept 2026; verifícalos si puedes)
- Los custom commands se fusionaron con los skills. `.claude/commands/x.md` sigue
  funcionando, pero se prefiere `.claude/skills/x/SKILL.md`, que admite scripts y
  archivos de soporte.
- `disable-model-invocation: true` hace que solo el usuario pueda invocar el skill.
- `allowed-tools` solo aplica al turno en que se invoca el skill. En un flujo interactivo
  de varios turnos, los permisos de git y scripts deben ir en `.claude/settings.json`.
- El SKILL.md no se relee en turnos posteriores. Tras la compactación de contexto solo se
  conservan sus primeros ~5,000 tokens. Hay que mantenerlo corto y mover las reglas a
  archivos de soporte.
- Los hooks (PreToolUse / PostToolUse) pueden declararse en el frontmatter del skill y
  aplican reglas de forma determinista, no solo como sugerencia.
- Existe `${CLAUDE_SESSION_ID}` para identificar logs por sesión.
- En Windows, `shell: powershell` evita depender de Git Bash. Scripts en Python evitan
  el problema en ambos casos.
